## Story
As Marketing, I register a client, the system gives them their reference number, and if the phone I
typed is already on file it tells me **whose** — and then lets me decide.

## What Karim ruled, and what it cost
Two rulings landed on this story, and one of them reversed a database constraint.

**Ruling 7 — client codes are generated.** Sequential, of the form `C-10001`, with manual entry and
later editing both forbidden, *"so a code is a stable reference for extracts and ledgers rather than
something a person can mistype or change"* (`spec.md` §2 amendment). **This closes D-040's first
half**, which had flagged `Client.Code` as a required field `spec.md` never asked for. It was right
to flag, and the answer is that it should exist.

**Ruling 8 — duplicate phones are allowed, with a warning.** Karim: *"a corporate client and its CEO
might be registered as two separate entities sharing the same contact number."*

> **"Deduplicated by phone" is a warning, not a refusal.** A repeated number shows the operator which
> client already holds it and asks whether to proceed. **It does not block the save.**
> — `spec.md` §2, amended

**This is the direction that costs something, and the story must carry the cost rather than bury it.**
`ux_clients_phone` was a **unique index** — the database refused the save outright. It is now
`ix_clients_phone`, non-unique. Nothing prevents two client records for one person any more; the
control has moved from the database to a human reading a warning, and a human dismissing a warning is
a well-understood failure mode.

**So the matching is more load-bearing after this ruling, not less.** D-049 says it plainly: *"a
missed match used to mean a wrongly-accepted save; it now means a warning nobody sees."* The match
runs on the normalised phone, and the normalisation is the mitigation.

## Permissions, money, audit, i18n
- **Permissions:** `ClientManage`, `CompanyWide`, Marketing and Owner. **`Role.Client` must not hold
  it** — a portal user reaching the client master would see every other client, which §12 forbids
  absolutely.
- **Money:** moves no money and stores no money. Rule 12 is the one to watch: a "credit limit" or
  "balance" field on this form would be a stored balance, which CLAUDE.md forbids outright.
- **Audit:** `Created` on `Client`, actor = the Marketing user, after-state carrying the generated
  code and the kind. **Where the save proceeded past a duplicate-phone warning, the record says so
  and names the client that was matched.** That is the only durable trace that a human made the call,
  and it is what a later question about two client records will be answered from.
- **i18n:** `clients.create.title`, `clients.field.code` (read-only, with
  `clients.field.code.generated_notice`), `clients.field.name`, `clients.field.phone`,
  `clients.field.alternate_phone`, `clients.field.email`, `clients.field.address`,
  `clients.field.kind`, `clients.kind.individual`, `clients.kind.corporate`,
  `clients.duplicate.warning_title`, `clients.duplicate.warning_body`,
  `clients.duplicate.matched_archived`, `clients.duplicate.open_existing`,
  `clients.duplicate.proceed`, and the existing `errors.master.name_required`,
  `errors.phone.required`. **Every new key in both `ar.json` and `en.json`.**

## Acceptance criteria
**AC-119-A — a client is registered, and the system names them**
Given I am signed in as Marketing
When I register a client with a name, a phone and a kind
Then the client exists, is active, carries a generated code of the form `C-10001`, and an audit record names me

**AC-119-B — the codes run in sequence and are never typed** *(fails if the rule is broken)*
Given the last client created carries `C-10001`
When the next client is registered
Then it carries `C-10002`
And a request that supplies its own code has that value ignored or refused — under no circumstances stored

**AC-119-C — the same phone in three formats warns once, about the same client** *(fails if the rule is broken)*
Given a client "شركة النور" registered with `01001234567`
When a registration is attempted with `+20 100 123 4567`, and again with `0020 100 1234567`
Then each returns a warning that names **شركة النور**
And neither is refused

**AC-119-D — the warning does not block the save** *(fails if the rule is broken)*
Given the warning of AC-119-C
When the operator proceeds
Then a second client is created with the same phone
And both clients exist, each with its own code

**AC-119-E — the decision is in the trail** *(fails if the rule is broken)*
Given a client saved past a duplicate-phone warning
When its audit record is read
Then the record shows that a duplicate was matched and names the client it matched

**AC-119-F — an archived match still warns, and says it is archived**
Given an archived client with phone `01001234567`
When a new client is registered with that phone
Then the warning fires, names the archived client and marks it archived, and the save is still permitted

**AC-119-G — a portal client cannot reach the client master** *(fails if the rule is broken)*
Given I am a `Role.Client` user
When I list, read or create a client
Then every attempt is refused with 403 — no client ever sees another client's data

**AC-119-H — nobody outside Marketing and the Owner may register one**
Given I am Finance, then Technical Office, then HR, then a Site Engineer
When each attempts to register a client
Then each is refused with 403

**AC-119-I — no money on the record** *(fails if the rule is broken)*
Given the client entity, its API contract and its database table
When each is inspected
Then none carries a balance, a credit limit or any other stored money field

**AC-119-J — no withholding category on the record** *(fails if the rule is broken)*
Given the client entity, its API contract and its database table
When each is inspected
Then none carries a withholding category — it lives on the contract now (D-049 ruling 9)

**AC-119-K — an individual cannot be given a tax registration number**
Given kind `Individual`
When a tax registration number is supplied
Then it is refused with `errors.master.individual_does_not_withhold` (KAFF-120)

## Not in this story
Editing (KAFF-121), archiving (KAFF-123), listing and searching (KAFF-124). The individual-withholding
enforcement itself (KAFF-120). Setting a contract's withholding rate — that left slice 1 with ruling 9
and is **KAFF-416**, slice 4. Portal logins for clients: slice 8.

**Merging two clients that already exist.** Nothing in `spec.md` describes a merge, and building one
would be inventing a rule about which record wins. **It is worth saying that ruling 8 makes a merge
more likely to be wanted, not less** — the duplicates it permits are the population a merge would
operate on. If Kaff asks for one, it is Karim's decision and a new story.

## An architect's note — **N6**
The generator is slice 1's work (D-049) and its shape is not a business question. Two clients created
in the same instant must not receive the same code; `ux_clients_code` is unique, so a naive
read-max-and-add-one loses the race as a failed insert rather than as a duplicate. Whether that is a
database sequence, a counter row taken under lock, or a retry is Nabil's and the Architect's, recorded
as **N6**. **What is not open:** the format, the fact that it is sequential, and that nobody can type
one.
