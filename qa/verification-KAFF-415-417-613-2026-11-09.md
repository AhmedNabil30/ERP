**Findings on KAFF-417**

- F-417-1 (defect, low). The quotation groups lines **by run, not by باب**. `printGroups` starts a new group whenever `babCode` differs from the previous line, and lines come in `Position` order, which is insertion order (`Boq.AddLine` uses `_lines.Count + 1`). A BOQ built as باب A, باب B, باب A prints باب A twice. AC-417-E says "grouped by باب". The fix is to group by `babCode` regardless of order. No test covers interleaved باب.
- F-417-2 (audit question, for Nabil, not a breach as built). Becoming archived writes no audit record, because nothing is written: archive is derived on read from `FollowUpStartedOn`, which is audited at creation and at every reopen, plus the period. Read literally, `CLAUDE.md` asks for an audit record on every state *change*. No stored state changes here, and D-207 says "No new state is added". The project still visibly changes behaviour, though: it leaves the list and refuses signature. The moment it archived can be reconstructed only while `FollowUpPeriod.Days` stays the same. If the period is later changed in code, past archive moments move retroactively and no record shows when a project actually archived. My verdict is that this does not breach `CLAUDE.md` as written, but it is a gap Nabil should rule on: either accept derived archive as not a state change, or record it.
- F-417-3 (deploy effect). Migration `20261109184609_ProjectFollowUp` backfills `follow_up_started_on = created_at`. Any unsigned project still in Setup and created more than 30 days before the deploy is archived the moment the migration runs, with no audit record (see F-417-2). That is what Q-208-2 says ("starts at creation"), so the behaviour is the ruled one, but it lands on a stale project all at once. Measured on the local `kaff` database: 9 projects, 6 unsigned in Setup, **0** archived by the backfill. The demo project `فيلا 47` is signed and Active, so it is unaffected. `scripts/seed-demo-boq.mjs` signs the demo project when it seeds it (unless `--no-sign`), so a freshly seeded demo is unaffected. One local row, `مشروع قديم بلا توقيع`, has `follow_up_started_on` set to 2026-09-10, before its `created_at` of 2026-11-09, which means it was back-dated by hand for a UI shot. No route can produce that.
- F-417-4 (test hygiene, no assertion lost). Commit 0b554cc changed the seeded `createdAt` from the fixed `Now` to `DateTimeOffset.UtcNow` in 37 test files (412+/80-). I read every changed line. Only the `Project.Create` creation argument changed. No assertion compares a project's `CreatedAt`; the one `CreatedAt` assertion in the changed files (`ClosureEndpointTests.cs:371`) is on a posting. The tests' `TestClock` stays at a fixed past date, so `FollowUpStartedOn` lies after the handler's clock and `IsArchived` is false, which is the intent. The cost is that these fixtures now depend on the wall clock. If a `TestClock` is ever set 30 or more days after the real date, those projects archive and signing fails with `errors.project.archived`. Commit 0b554cc also added a BOM to `DailyLogTests.cs`.
- F-417-5 (drift risk, low). The workspace preview hardcodes `DESIGN_RATE_PER_SQUARE_METRE = 450n` (`project-workspace-page.ts:63`). The stored fee is computed by the server from `ContractDefaults.DesignRatePerSquareMetre`, so the stored value cannot be wrong. If the rate changes in `ContractDefaults` alone, though, the confirmation text will show the client the wrong fee before signature. The arithmetic is exact (BigInt), with no float.
- F-417-6 (gap outside the criteria). Archive blocks signing only. An archived project can still have its BOQ edited, and an archived Design project can still be converted to execution. AC-417-J names only signing, so this is not a failure.

**Findings on KAFF-613**

- F-613-1 (defect, low). The device time is captured **after** the location fix, not at the press. `checkIn()` awaits `currentPlace()` (timeout `LOCATION_TIMEOUT_MS = 15_000`, `enableHighAccuracy`, `maximumAge: 0`) and only then builds `occurredAt: localIso(new Date())`. The recorded time can therefore be up to 15 seconds after the press. AC-613-G says "Device time is the time the button was pressed". The fix is to take `new Date()` before awaiting the place.
- F-613-2 (stale documentation). The XML comments still describe D-207's reversed default. `RecordCheckIn/Handler.cs` says "Never refuses for location (Q-207-3, Q-207-4): the entry carries a flag instead", and `RecordCheckIn/Request.cs` says "Location is optional: a phone that refuses it is still recorded, and flagged". Both are false since 0b554cc. They are comments only, but a later session reading them could rebuild the wrong rule.
- F-613-3 (answers the Scrum Master's point). The scalar `checkIn` / `checkOut` on `GET .../daily-logs/mine` are still populated, and from the new route too. `GetMyLog` takes `Current(DailyLogField.CheckIn)` from the same `field_entries` rows that `RecordCheckIn` writes, as the latest by `OccurredAt`. No API test asserts the scalar after a new-route check-in, so this is shown by reading the code only. The web client uses the scalars only in `isEmpty`.

## Cross-cutting checks

### `ClosureRouteGateTests.RequirementOf` (changed in 0d76c30)

The helper now returns the project-scoped requirement when a route carries one, and otherwise the first requirement
it finds. The question was whether `Every_route_under_a_project_demands_a_permission_scoped_to_a_project` can still
fail on a route whose only policy is company-wide.

**It can.** For a route with a single company-wide policy, `first` is that policy and is returned. `UngatedProjectRoutes`
then flags it because `Scope.Source == None`. The positive control
`The_route_check_sees_a_project_route_with_no_permission_or_the_wrong_scope` feeds exactly that case
(`probe-company`, `SnagManage` with `ProjectScope.None`) and a route with no policy through the same function, and asserts
that both are reported. The control still passes, so the absence test is still able to fail.

Accepting a route that carries both a company-wide policy and a project-scoped one is correct, because ASP.NET Core
requires every policy to pass.

There is one narrow weakening. `A_route_demanding_a_closure_permission_is_a_closure_route_wherever_it_was_written` now
looks only at the project-scoped requirement when there are two. A route outside the closure namespace could demand a
closure-only permission as its *company-wide* second policy and not be reported. No such route exists today. The
synthetic control has no two-policy case.

### Separate accounts per project, including the accounts opened late

`ProjectAccountSetFactory.Open` names every account `{project code}-{suffix}`, and the database holds
`ux_accounts_project_dimension` UNIQUE on `(type, project_id, party_type, party_id)` plus `ux_accounts_code` UNIQUE.
A `-REV` or `-CREC` opened at signature therefore cannot duplicate an existing account, and cannot land on another
project. On the local database, the UI lane's `تنفيذ فيلا الشروق` (Lump Sum, `DesignToExecution`) has its own five
`PRJ-45BD91F2-*` accounts, and its design `تصميم فيلا الشروق` keeps `PRJ-143C7835-CONSULT` / `-DREV`. No account
is shared. The Cost Plus `ClientReceivable` opened at signature is new structure, recorded in D-209. It is the client
sub-ledger `spec.md` §6.3 places under every project account, so I find no conflict with the spec.
