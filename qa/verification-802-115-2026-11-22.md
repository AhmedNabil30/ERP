### Findings

- **F-802-1 (minor, test strength).** AC-802-M's test cannot fail on the rule it names, as described above. It should
  assert on `Reason` alone, on the posting's audit row.
- **F-802-2 (minor, concurrency).** `RejectHoldRelease/Handler.cs` takes no project row lock, and `HoldReleaseRequest`
  has no concurrency token. An approval and a rejection racing on the same waiting request can both pass
  `EnsureMayDecide`; the last save wins, so the request can read `Rejected` while the `HoldRelease` posting exists.
  Money stays safe (one posting; the once-check refuses any later request), but the closure read would then show a
  rejection reason for a hold that was released. Taking the same `FOR UPDATE` lock in the rejection handler closes it.
- **F-802-3 (observation, not an AC).** The story still says "No UI criterion is carried here", yet 07db3d7 built the
  screen. The screen was judged only for consistency with the server: Finance sees «طلب الإفراج عن الحجز», then
  «بانتظار المالك» with no button; the Owner sees «اعتماد» and «إرجاع» with a required reason; after a return Finance
  sees the reason and may ask again. `canDecide` also hides the decision from the asker. The builder's screenshot
  `qa/shots-hold-release/closure-owner-approve-390.png` shows two filled primary buttons on the Owner's screen at once
  (the header slot «بدء فترة الضمان» and «اعتماد»), and two explanatory sentences under the hold figure, which the
  "screens explain themselves" rule discourages. Route to the designer; not a verdict item. The screen was not driven
  in a browser by this pass.

### The warranty question: may the warranty start before the hold is released?

`spec.md` section 11: "Warranty starts automatically on the handover date." Section 5.1: the hold "releases once, in
full, at handover". Section 13: `Handover -> UnderWarranty -> Closed`. Section 11: a project closes only when the hold is
released.

So, per the spec, **the warranty has already started when the project enters `Handover`**, whether or not the hold is
released. The code agrees: `warranty_ends_on` is stamped at handover (AC-802-H). The spec does not order the
`Handover -> UnderWarranty` state move against the release, and does not say what triggers that move: that is Q110, and
AC-802-F is HELD on it. The code allows the release in both `Handover` and `UnderWarranty` (`PostingProjectStatePolicy`,
assumed, not ruled), so pressing the button while the request waits does not strand the release.

Two consequences:

1. The label «بدء فترة الضمان» ("start the warranty period") is inaccurate against section 11. Nobody starts the
   warranty; it started automatically on the handover date. The button performs the `Handover -> UnderWarranty` state
   move, whose trigger is unruled (Q110).
2. Offering that move as the Owner's header primary while a hold release waits for the same Owner puts a manual,
   unruled step ahead of the pending money approval. "Releases at handover" reads as the release belonging to the
   `Handover` stage; the spec does not forbid releasing under warranty, but does not invite it either.

Not NOT MET against any criterion (AC-802-F is HELD). It is a question for Nabil and Karim, attached to Q110: should
`Handover -> UnderWarranty` be automatic at handover, as "starts automatically" suggests; and if it stays manual, should
it wait for the hold release?

`VERIFIED verdict=CONDITIONAL`. Every judged criterion is MET; F and G are HELD on Q110 and Q111. Conditions: F-802-1
(the AC-802-M test cannot fail) and F-802-2 (the rejection takes no row lock).

## Money and permission rules, checked on every pass

- No `float` or `double` near money in the new code: `HoldReleaseRequest` stores no amount at all; the approval uses
  `Money` from the ledger sum. Live amount `38810.0400` (decimal, 4 places).
- No stored balance: `hold_release_requests` has no amount or balance column (migration `HoldReleaseRequests`).
- No posting update or delete path added: the new routes create a request, decide it, and append one posting.
- The hold is never debited before handover: refused at the request and again at the approval, by the domain, and by
  the database trigger. Verified clean.
- Role and assignment server-side: all three new routes are `RequirePermission(..., ProjectScope.FromRoute())`, pinned
  in `ClosureRouteGateTests`.
- Nobody creates and approves the same movement: disjoint catalogue rows plus `SeparationOfDuties.EnsureDifferentActor`.
